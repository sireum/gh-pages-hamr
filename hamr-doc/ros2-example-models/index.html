    ROS 2 Example Models

    The three model variants used by the ROS 2 chapters, in full.

    Each is a rung on the same system: a wheel encoder feeding a pilot that drives turtlesim. They differ only in how much the model says, and the chapters walk that difference. The sources are reproduced here so they can be read without leaving the browser.

    These are the models HAMR’s own test suite exercises.

    The structure variant

    Nothing names a topic, and turtlesim is not modeled. Topic names are derived from the receiving port’s path, and the two turtlesim edges are reconciled by deployment remaps.

    Used by ROS 2 Component Development.

    TurtleControl_Structure.sysml

    //@ HAMR: --platform ros2 --ros2-output-workspace-dir ../../hamr/structure

/*============================================================
    Turtle Control -- structure variant

    A minimal HAMR ROS 2 system used by the "Code-Level Development
    for ROS 2" documentation.  A micro-ROS node reads a wheel encoder
    on an MCU, an rclcpp node closes a control loop, and stock
    turtlesim is the plant.

        encoder --speed/overspeed--> pilot --cmdVel--> (turtlesim)
              <-- mode/trim ----------/    <--pose----/

    This variant models STRUCTURE only: components, ports,
    connections, and the platform-provided payload types (see
    RosMessages.sysml and Turtlesim.sysml -- the latter declares the
    turtlesim message type only; the turtlesim NODE is off-model
    here).  There are no naming
    properties, so every port keeps its default (port-path-derived)
    topic name and binding to the stock node is left entirely to
    deployment -- see REMAPPING on Pilot below.

    turtlesim is left OFF-MODEL here: no component declaration and no
    connection, bound purely in the deployment layer.  pilot.cmdVel
    and pilot.pose are therefore boundary ports.  The naming/ variant
    declares turtlesim as a platform-provided component and adds
    model-carried topic names and namespaces, which removes both
    remaps and brings type checking and the generation-time name
    checks to those two edges.

    Port kinds are chosen to exercise all three categories in both
    directions, and to cover both ways an arriving message can be
    taken up -- by dispatching a sporadic thread, and by waiting in a
    queue for a periodic one:

      speed     -- event data (dispatches the sporadic pilot)
      overspeed -- event      (a bare alarm; also dispatches the pilot)
      mode      -- data       (a setting, sampled by the periodic encoder)
      trim      -- event data (waits for the periodic encoder's next dispatch)
      cmdVel    -- data       (a continuous command)
      pose      -- data       (sampled state; turtlesim publishes at 62.5 Hz
                               but pilot reads only the latest on dispatch)

    The encoder is PERIODIC, so an arrival on trim cannot dispatch it.
    Codegen holds the arrival until the next period and consumes it
    there.  Only the AADL default Queue_Size of 1 is supported, so a
    second arrival within one period replaces the first.
  ============================================================*/

package TurtleControl_Structure {
    private import HAMR::*;

    part def TurtleControlSystem :> System {
        part proc : TurtleControlProcess;
    }

    part def TurtleControlProcess :> Process {
        // subcomponents
        part encoder : Encoder;
        part pilot   : Pilot;

        // connections
        connection cSpeed     : PortConnection connect encoder.speed     to pilot.speed;
        connection cOverspeed : PortConnection connect encoder.overspeed to pilot.overspeed;
        connection cMode      : PortConnection connect pilot.mode        to encoder.mode;
        connection cTrim      : PortConnection connect pilot.trim        to encoder.trim;

        // pilot.cmdVel and pilot.pose are unconnected: their peer is the stock
        // turtlesim node, which this variant leaves off-model and binds by
        // remapping (see REMAPPING on Pilot)
    }

    // The micro-ROS node: firmware on an MCU that samples a wheel encoder.
    part def Encoder :> Thread {
        // A setting rather than a stream of commands, so a DataPort: the
        // encoder samples whatever the pilot most recently published, and a
        // missed update is superseded rather than lost.
        in port mode : DataPort { in :>> type : OperatingMode; }

        // A discrete command, so an event data port rather than a data port: it is
        // an instruction to act, and skipping one is not the same as acting on the
        // newer one.  Because this node is PERIODIC an arrival cannot dispatch it,
        // so the arrival waits and is consumed at the next period.  Only the AADL
        // default Queue_Size of 1 is supported, so a second arrival within one
        // period replaces the first.
        in port trim : EventDataPort {
            in :>> type : TrimCommand;
        }

        // EventDataPort: each reading is a discrete message the pilot should
        // process, and its arrival is what dispatches the (sporadic) pilot.
        // A DataPort here would give the pilot nothing to wake on.
        out port speed : EventDataPort { out :>> type : WheelSpeed; }

        // EventPort: the alarm carries no payload -- the fact of it is the
        // whole message.  Codegen gives event ports an empty message type
        // (Empty.msg in the generated interfaces package).
        out port overspeed : EventPort;

        // Periodic: the encoder is sampled on a clock, independent of any
        // arriving message.  Its in data port is read at the top of each
        // period.
        attribute :>> Dispatch_Protocol = Periodic;
        attribute :>> Period = 100 [ms];

        // Ros_Node_Kind is what selects the micro-ROS backend for this thread.
        attribute :>> Ros_Node_Kind = microRos;
    }

    // REMAPPING: cmdVel and pose are boundary ports -- their peer is the stock
    // turtlesim node, which this variant does not model.  Each keeps its
    // path-derived default topic, so both need a manual bind at launch:
    //   ros2 run ... --ros-args \
    //     -r proc_pilot_cmdVel:=/turtle1/cmd_vel \
    //     -r proc_pilot_pose:=/turtle1/pose
    // turtlesim subscribes to the relative "turtle1/cmd_vel" and publishes the
    // relative "turtle1/pose"; launched without a namespace both resolve at the
    // root.  Write the match sides relative so they keep matching if this node
    // is later namespaced.
    part def Pilot :> Thread {
        // Two triggering ports: either an encoder reading or an overspeed alarm
        // dispatches the pilot, and codegen generates a handler for each.
        in port speed     : EventDataPort { in :>> type : WheelSpeed; }
        in port overspeed : EventPort;

        // Sampled, not triggering: turtlesim publishes pose continuously, but
        // the pilot reads the latest value when it is dispatched by one of the
        // ports above rather than waking on every pose message.
        in port pose : DataPort { in :>> type : turtlesim::Pose; }

        out port cmdVel : DataPort { out :>> type : geometry_msgs::Twist; }
        out port mode   : DataPort { out :>> type : OperatingMode; }

        // The sending counterpart of encoder.trim.  How an arrival is buffered is
        // a property of the RECEIVING end, so nothing about it is declared here.
        out port trim : EventDataPort { out :>> type : TrimCommand; }

        attribute :>> Dispatch_Protocol = Sporadic;

        // Optional -- ros2 is the default.  Ros_Node_Kind only ever needs to be
        // declared to opt INTO micro-ROS: codegen treats a thread as micro-ROS
        // only on an explicit microRos value, so an absent property and an
        // explicit ros2 mean the same thing.  Stated here for contrast with
        // Encoder above, where the property is load-bearing.
        attribute :>> Ros_Node_Kind = ros2;

        // No Period.  AADL reads Period on a sporadic thread as a minimum
        // inter-arrival time, but nothing generated enforces it and the ROS 2
        // backend ignores the property entirely for sporadic components, so
        // declaring one would state a bound no artifact honors.
    }

    // Data Types
    //
    // These are ordinary model-defined types, so codegen emits a .msg file for
    // each into the generated <system>_interfaces package -- the contrast with
    // the platform-provided types in RosMessages.sysml and Turtlesim.sysml,
    // for which no .msg is emitted and the native ROS type flows instead.

    part def WheelSpeed :> Data {
        part rpm : Base_Types::Float_32;
    }

    part def TrimCommand :> Data {
        part deltaRpm : Base_Types::Float_32;
    }

    enum def OperatingMode {
        enum Idle;
        enum Run;
        enum Fault;
    }
}

    Turtlesim.sysml

    /*============================================================
    The turtlesim ROS package -- message type only in this variant.

    Same structural convention as RosMessages.sysml (SysML package =
    ROS package, part def = message name), so turtlesim::Pose denotes
    turtlesim/msg/Pose.

    WHY THIS FILE EXISTS EVEN THOUGH TURTLESIM IS OFF-MODEL

    This variant leaves the turtlesim NODE unmodeled -- there is no
    component declaration and no connection for it (see the REMAPPING
    note in TurtleControl_Structure.sysml).  A message TYPE is a
    separate matter: pilot.pose is typed by turtlesim::Pose, and a
    type must be declared wherever it is used as a port type,
    regardless of whether the component on the other end of the topic
    is modeled.

    The naming/ variant adds turtlesim_node to this same file, since
    the ROS package turtlesim contains both the message and the
    executable.  Comparing the two copies of this file is therefore
    the whole of the platform-provided-COMPONENT delta between the
    variants.

    MIRROR FIELDS

    Unlike the opaque geometry_msgs::Twist in RosMessages.sysml, Pose
    carries mirror fields.  Mirror fields are specification-level
    projections of the native type, not layout claims: they exist so
    that the model can speak about the value.  Codegen still emits no
    .msg file -- the native ROS type flows through the topic either
    way -- so the difference between this type and Twist shows up in
    what the model can say, not in what is generated.

    Pose is mirrored completely here because its native definition is
    flat and small.  A mirror may also be partial: mirroring only the
    fields a model needs is the normal case for larger messages.
  ============================================================*/

package turtlesim {
    private import HAMR::*;

    // turtlesim/msg/Pose
    //   native: float32 x, y, theta, linear_velocity, angular_velocity
    part def Pose :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;

        part x                : Base_Types::Float_32;
        part y                : Base_Types::Float_32;
        part theta            : Base_Types::Float_32;
        part linear_velocity  : Base_Types::Float_32;
        part angular_velocity : Base_Types::Float_32;
    }
}

    RosMessages.sysml

    /*============================================================
    Platform-provided ROS 2 message types

    Mirrors of preexisting ROS 2 message types used by the Turtle
    Control system.  Structural convention (see doc/ros/PlatformProvidedTypes-design.md):
    SysML package name = ROS package name, part def name = message
    name, so geometry_msgs::Twist denotes geometry_msgs/msg/Twist.

    Twist is declared OPAQUE -- the minimum declaration, no fields.
    That is enough for codegen: it emits no .msg file for the type,
    uses the native ROS type as the payload of every port and topic
    carrying it, and adds geometry_msgs to the generated package
    dependencies.  What an opaque declaration does NOT give you is a
    vocabulary: nothing in the model can speak about the value's
    fields, and codegen generates no example builder for it, so
    application code constructs a Twist with native rclcpp calls.

    turtlesim::Pose, in Turtlesim.sysml, is the contrasting case: the
    same provenance, but with mirror fields.

    NOTE: Type_Provenance is a HAMR extension defined in the
    sysml-aadl-libraries.
  ============================================================*/

package geometry_msgs {
    private import HAMR::*;

    // geometry_msgs/msg/Twist
    //   native: Vector3 linear ; Vector3 angular
    part def Twist :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;
    }
}

    The naming variant

    The same system with model-carried topic names, a namespace, and turtlesim declared as a platform-provided component. Both deployment remaps are gone.

    Used by ROS 2 Topic Naming and Platform Integration.

    TurtleControl_Naming.sysml

    //@ HAMR: --platform ros2 --ros2-output-workspace-dir ../../hamr/naming

/*============================================================
    Turtle Control -- naming variant

    The same system as the structure/ variant, with two additions:
    model-carried NAMING (Ros_Namespace, Ros_Topic_Name) and stock
    turtlesim declared as a PLATFORM-PROVIDED COMPONENT.  Together
    these remove every deployment remap the structure variant needed
    and put the turtlesim edges under generation-time checking.

        encoder --/rover/speed------------> pilot --/turtle1/cmd_vel--> turtle
              <--/rover/proc_encoder_mode--/      <--/turtle1/pose-----/

    WHAT CHANGED FROM structure/

    1. encoder and pilot are placed in the "rover" namespace, at
       their USAGE SITES -- a namespace is deployment configuration,
       so the part defs stay deployment-neutral.  turtle is
       deliberately left UN-NAMESPACED, so it keeps the root-relative
       names a stock turtlesim actually uses.

    2. turtle is declared (see Turtlesim.sysml), so cVel and cPose
       are real connections.  Codegen emits no code for it, only
       deployment artifacts: a launch entry and a package dependency.

    3. Three ports carry explicit topic names, and they illustrate
       the three cases:

       - turtle.cmdVel and turtle.pose declare the stock node's own
         built-in relative names ("turtle1/cmd_vel", "turtle1/pose").
         These stay at the DEFINITION (Turtlesim.sysml) because they
         are facts about the node, not deployment configuration.

       - encoder.speed declares the relative "speed" at its USAGE
         SITE.  That is deployment configuration, hence the usage-site
         refinement (port :>> speed { ... }).

       - pilot declares NO topic names at all.  Topic names are
         resolved PER EDGE: an explicit name on either endpoint
         governs both ends, so pilot.speed follows encoder.speed and
         pilot.cmdVel/pilot.pose follow the turtle's names.

    4. overspeed, mode and trim declare nothing anywhere,
       so they keep their path-derived defaults.  Naming is per-port,
       not all-or-nothing.

    RELATIVE VS. ABSOLUTE

    A relative name resolves against the DECLARING node's namespace,
    which is why the declaring end matters:

      encoder.speed  "speed"            + namespace rover -> /rover/speed
                                          pilot.speed is bound to the
                                          resolved /rover/speed, not to
                                          "speed" under its own namespace
                                          (which here would be the same
                                          topic, but need not be)

      turtle.cmdVel  "turtle1/cmd_vel"  + no namespace    -> /turtle1/cmd_vel
                                          pilot, though itself in /rover,
                                          publishes to /turtle1/cmd_vel --
                                          the namespace does not follow it

    NOTE: Ros_Topic_Name, Ros_Namespace and the provenance properties
    are HAMR extensions defined in the sysml-aadl-libraries; see
    doc/ros/PlatformProvidedTypes-design.md.  HAMR_AADL_Preview must be
    imported BEFORE HAMR -- it supplies the port defs that carry
    Ros_Topic_Name, and with the imports reversed the unqualified port
    names resolve to the plain AADL defs and the attribute is silently
    dropped.
  ============================================================*/

package TurtleControl_Naming {
    private import HAMR_AADL_Preview::*;
    private import HAMR::*;

    part def TurtleControlSystem :> System {
        part proc : TurtleControlProcess;
    }

    part def TurtleControlProcess :> Process {
        // subcomponents -- deployment configuration (node namespace, and any
        // topic name that is a deployment choice rather than a fact about the
        // node) is assigned here at the usage sites, keeping the part defs
        // deployment-neutral

        part encoder : Encoder {
            attribute :>> Ros_Namespace = "rover";

            port :>> speed {
                // relative; composes with this node's namespace -> /rover/speed.
                // pilot.speed declares nothing and is bound to the resolved
                // absolute form.
                attribute :>> Ros_Topic_Name = "speed";
            }

            // overspeed declares no name and keeps its path-derived default
        }

        part pilot : Pilot {
            attribute :>> Ros_Namespace = "rover";

            // no port refinements at all: every one of pilot's named topics is
            // determined by its peer (per-edge resolution), and the rest keep
            // their path-derived defaults
        }

        // platform-provided stock node (see Turtlesim.sysml): the usage name
        // 'turtle' becomes the launch-entry node name.  Deliberately NOT
        // namespaced -- a stock turtlesim launched bare uses root-relative
        // names, and leaving it there is what makes pilot's cmdVel/pose
        // topics escape the rover namespace.
        part turtle : turtlesim::turtlesim_node;

        // connections
        connection cSpeed     : PortConnection connect encoder.speed     to pilot.speed;
        connection cOverspeed : PortConnection connect encoder.overspeed to pilot.overspeed;
        connection cMode      : PortConnection connect pilot.mode        to encoder.mode;
        connection cTrim      : PortConnection connect pilot.trim        to encoder.trim;

        // with turtle modeled, both turtlesim edges are explicit: datatype
        // agreement and the generation-time topic-name checks now apply where
        // the structure variant had only an unchecked deployment remap
        connection cVel  : PortConnection connect pilot.cmdVel to turtle.cmdVel;
        connection cPose : PortConnection connect turtle.pose  to pilot.pose;
    }

    // Unchanged from the structure variant apart from the naming assigned at
    // the usage sites above -- the definitions themselves stay
    // deployment-neutral.
    part def Encoder :> Thread {
        in  port mode      : DataPort      { in  :>> type : OperatingMode; }
        out port speed     : EventDataPort { out :>> type : WheelSpeed; }
        out port overspeed : EventPort;

        // This node is PERIODIC, so an arrival here cannot dispatch it: the arrival
        // waits and is consumed at the next period.  Only the AADL default
        // Queue_Size of 1 is supported, so a second arrival within one period
        // replaces the first.
        in port trim : EventDataPort {
            in :>> type : TrimCommand;
        }

        attribute :>> Dispatch_Protocol = Periodic;
        attribute :>> Period = 100 [ms];

        attribute :>> Ros_Node_Kind = microRos;
    }

    part def Pilot :> Thread {
        in  port speed     : EventDataPort { in  :>> type : WheelSpeed; }
        in  port overspeed : EventPort;
        in  port pose      : DataPort      { in  :>> type : turtlesim::Pose; }

        out port cmdVel : DataPort { out :>> type : geometry_msgs::Twist; }
        out port mode   : DataPort { out :>> type : OperatingMode; }

        // How an arrival is buffered is a property of the receiving end, so nothing
        // about it is declared here
        out port trim : EventDataPort { out :>> type : TrimCommand; }

        attribute :>> Dispatch_Protocol = Sporadic;

        attribute :>> Ros_Node_Kind = ros2;
    }

    // Data Types
    part def WheelSpeed :> Data {
        part rpm : Base_Types::Float_32;
    }

    part def TrimCommand :> Data {
        part deltaRpm : Base_Types::Float_32;
    }

    enum def OperatingMode {
        enum Idle;
        enum Run;
        enum Fault;
    }
}

    Turtlesim.sysml

    /*============================================================
    The turtlesim ROS package: its message type, and the stock node
    itself declared as a PLATFORM-PROVIDED COMPONENT.

    Structural convention (see doc/ros/PlatformProvidedTypes-design.md):
    SysML package name = ROS package name; for a message, part def
    name = message name (turtlesim::Pose -> turtlesim/msg/Pose); for a
    component, part def name = executable name
    (turtlesim::turtlesim_node -> `ros2 run turtlesim turtlesim_node`).
    Both live in this one package because the ROS package turtlesim
    contains both.

    The structure/ variant's copy of this file declares only Pose and
    leaves the node off-model.  Declaring the node -- the sole
    difference between the two copies -- is what brings the cVel and
    cPose connections back, and with them datatype checking and the
    generation-time topic-name checks.

    Codegen emits NO code for a platform-provided component -- only
    deployment artifacts: a launch entry (the subcomponent usage name
    becomes the node name) and an exec_depend on the turtlesim package
    so `rosdep install` pulls the stock node.
  ============================================================*/

package turtlesim {
    private import HAMR_AADL_Preview::*;
    private import HAMR::*;

    // turtlesim/msg/Pose
    //   native: float32 x, y, theta, linear_velocity, angular_velocity
    part def Pose :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;

        part x                : Base_Types::Float_32;
        part y                : Base_Types::Float_32;
        part theta            : Base_Types::Float_32;
        part linear_velocity  : Base_Types::Float_32;
        part angular_velocity : Base_Types::Float_32;
    }

    part def turtlesim_node :> Thread {
        attribute :>> Component_Provenance = Provenances::Platform_Provided;

        // Optional: the structural convention above already yields
        // turtlesim/turtlesim_node.  Native_Name is the escape hatch for a node
        // whose package/executable names do not match the model's.
        // attribute :>> Native_Name = "turtlesim/turtlesim_node";

        // Periodic with data ports, and the two go together -- both follow from
        // how turtlesim actually runs: a ~16 ms frame update that consumes the
        // LATEST stored Twist, zeroing it after a 1 s command timeout, while the
        // subscription callback only stores.  That is last-value-wins sampling,
        // not queued event dispatch, so there is no arrival to dispatch on and
        // no queue to model.
        //
        // None of this reaches the ROS 2 backend -- no code is generated for a
        // platform-provided component -- so these attributes are for scheduling
        // analysis and for the reader.
        attribute :>> Dispatch_Protocol = Periodic;
        attribute :>> Period = 16 [ms];

        // The node's built-in topics, declared with their own RELATIVE names.
        // These stay here at the definition rather than at the usage site: they
        // are facts about the stock node, not deployment configuration.  With
        // this component left un-namespaced at its usage site, they resolve to
        // /turtle1/cmd_vel and /turtle1/pose.
        in port cmdVel : DataPort {
            in :>> type : geometry_msgs::Twist;

            attribute :>> Ros_Topic_Name = "turtle1/cmd_vel";
        }

        out port pose : DataPort {
            out :>> type : Pose;

            attribute :>> Ros_Topic_Name = "turtle1/pose";
        }
    }
}

    The logging variant

    The naming variant plus a logger node and the reserved rosout ports that feed it — ports that refer to a path the platform already provides.

    Used by Infrastructure-Provided Ports.

    TurtleControl_Logging.sysml

    //@ HAMR: --platform ros2 --ros2-output-workspace-dir ../../hamr/logging

/*============================================================
    Turtle Control -- logging variant

    The naming/ variant with one addition: a LOGGER node, and the
    INFRASTRUCTURE-PROVIDED PORTS that feed it.

        encoder --/rover/speed------------> pilot --/turtle1/cmd_vel--> turtle
              <--/rover/proc_encoder_mode--/      <--/turtle1/pose-----/
              \--/rosout-----------------------------------------> logger

    WHAT AN INFRASTRUCTURE-PROVIDED PORT IS

    Every port in the structure/ and naming/ variants is one the
    model DECLARES and codegen REALIZES: codegen creates the
    publisher or subscription, and application code drives it through
    a generated put_/get_ API.

    'rosout' is different.  Every ROS node already has a built-in
    /rosout log publisher, driven by the rcl logging infrastructure
    rather than by application code.  A port named 'rosout' does not
    declare a new thing -- it REFERS to that built-in one.  The name
    is therefore reserved: such a port must be an EventDataPort typed
    rcl_interfaces::Log, and its topic is pinned by the platform to
    /rosout, so the usual path-derived naming does not apply and a
    conflicting Ros_Topic_Name is an error.

    (A port with any OTHER name carrying rcl_interfaces::Log is
    entirely ordinary -- a log relay republishing filtered records on
    a custom topic is modeled that way, with no restrictions.)

    WHY THE PORTS ARE HERE AT ALL

    They direct codegen; they add no data plane.

      encoder.rosout (out, micro-ROS) -- the ENABLEMENT TRIGGER.  An
        rclcpp node publishes /rosout by default, but a micro-ROS
        node does not: its logging is console-only unless rcl logging
        is configured.  The port's presence is what makes codegen
        emit that setup and set the firmware flags.  Omit the port
        and the encoder's log records never leave the MCU.

      logger.rosout (in, rclcpp) -- makes codegen generate the
        /rosout subscription.  Nothing about /rosout is automatic on
        the consuming side: subscribing is a property of one port,
        not of the topic.

    Either side could be hand-wired after codegen instead.  Declaring
    the ports is how the model states the intent and gets the setup
    generated.

    WHAT IS DELIBERATELY NOT MODELED

    pilot has no rosout port, yet it still publishes to /rosout --
    rclcpp does that by default whether or not anyone models it.  The
    same is true of turtlesim.  /rosout is a many-writer topic and
    the logger will receive all of it.

    That is the point of the cLog connection below: on a topic
    everything writes to, the model records WHICH producer's flow it
    cares about.  Here that is the encoder, because the encoder is
    the one whose logging had to be deliberately enabled.
  ============================================================*/

package TurtleControl_Logging {
    private import HAMR_AADL_Preview::*;
    private import HAMR::*;

    part def TurtleControlSystem :> System {
        part proc : TurtleControlProcess;
    }

    part def TurtleControlProcess :> Process {
        part encoder : Encoder {
            attribute :>> Ros_Namespace = "rover";

            port :>> speed {
                attribute :>> Ros_Topic_Name = "speed";
            }
        }

        part pilot : Pilot {
            attribute :>> Ros_Namespace = "rover";
        }

        // The logger is namespaced like the other generated nodes.  That
        // affects its NODE name (/rover/logger) but not the topic it
        // subscribes to: /rosout is platform-pinned and absolute, so unlike
        // encoder.speed it does not compose with the namespace.
        part logger : Logger {
            attribute :>> Ros_Namespace = "rover";
        }

        part turtle : turtlesim::turtlesim_node;

        // connections
        connection cSpeed     : PortConnection connect encoder.speed     to pilot.speed;
        connection cOverspeed : PortConnection connect encoder.overspeed to pilot.overspeed;
        connection cMode      : PortConnection connect pilot.mode        to encoder.mode;
        connection cTrim      : PortConnection connect pilot.trim        to encoder.trim;

        connection cVel  : PortConnection connect pilot.cmdVel to turtle.cmdVel;
        connection cPose : PortConnection connect turtle.pose  to pilot.pose;

        // OPTIONAL, and it generates nothing.  Both endpoints are pinned to
        // /rosout and each side's code is already determined by its own port,
        // so codegen derives nothing from this edge -- not even type checking,
        // since port validation independently forces rcl_interfaces::Log on
        // both ends.
        //
        // It is here because it is the only place the model can say which
        // producer's log flow it cares about on a topic that everything
        // writes to.  Delete it and the generated code is byte-identical;
        // what is lost is the statement of intent.
        connection cLog : PortConnection connect encoder.rosout to logger.rosout;
    }

    part def Encoder :> Thread {
        in  port mode      : DataPort      { in  :>> type : OperatingMode; }
        out port speed     : EventDataPort { out :>> type : WheelSpeed; }
        out port overspeed : EventPort;

        // This node is PERIODIC, so an arrival here cannot dispatch it: the arrival
        // waits and is consumed at the next period.  Only the AADL default
        // Queue_Size of 1 is supported, so a second arrival within one period
        // replaces the first.
        in port trim : EventDataPort {
            in :>> type : TrimCommand;
        }

        // The reserved infrastructure port.  No publisher and no put_rosout API
        // are generated for it; what its presence does is make generated init
        // call rcl_logging_configure and set RCL_LOGGING_ENABLED in the emitted
        // colcon.meta, so this node's LOG_INFO/LOG_WARN/LOG_ERROR records reach
        // /rosout instead of only the console.
        out port rosout : EventDataPort {
            out :>> type : rcl_interfaces::Log;

            // Optional -- the reserved name already implies both, and codegen
            // rejects any other value.  Stated here because this is the variant
            // that teaches the mechanism.
            attribute :>> Port_Provenance = Provenances::Infrastructure;
            attribute :>> Ros_Topic_Name = "/rosout";
        }

        attribute :>> Dispatch_Protocol = Periodic;
        attribute :>> Period = 100 [ms];

        attribute :>> Ros_Node_Kind = microRos;
    }

    part def Pilot :> Thread {
        in  port speed     : EventDataPort { in  :>> type : WheelSpeed; }
        in  port overspeed : EventPort;
        in  port pose      : DataPort      { in  :>> type : turtlesim::Pose; }

        out port cmdVel : DataPort { out :>> type : geometry_msgs::Twist; }
        out port mode   : DataPort { out :>> type : OperatingMode; }

        out port trim : EventDataPort { out :>> type : TrimCommand; }

        // Deliberately NO rosout port.  The pilot is an rclcpp node, so it
        // publishes /rosout regardless -- the port would be documentation with
        // no generated consequence.  Leaving it off keeps the model's rosout
        // story about the node where the port actually changes something.

        attribute :>> Dispatch_Protocol = Sporadic;

        attribute :>> Ros_Node_Kind = ros2;
    }

    // Consumes the log stream.  An rclcpp node on purpose: a micro-ROS consumer
    // would need static receive buffers sized for Log's unbounded strings
    // (name, msg, file, function), and would pull every node's log traffic
    // across the agent link -- a real cost on a constrained transport.
    part def Logger :> Thread {
        // The reserved port on the consuming side.  Ordinary generation: this
        // produces a normal subscription to /rosout.  The topic name defaults
        // to /rosout and needs no declaration.
        in port rosout : EventDataPort {
            in :>> type : rcl_interfaces::Log;
        }

        // Sporadic: rosout is an in event data port, so each arriving record
        // dispatches the thread and every record is processed.  A DataPort here
        // would sample the newest record and drop the rest, which for a log is
        // exactly wrong.
        attribute :>> Dispatch_Protocol = Sporadic;

        attribute :>> Ros_Node_Kind = ros2;
    }

    // Data Types
    part def WheelSpeed :> Data {
        part rpm : Base_Types::Float_32;
    }

    part def TrimCommand :> Data {
        part deltaRpm : Base_Types::Float_32;
    }

    enum def OperatingMode {
        enum Idle;
        enum Run;
        enum Fault;
    }
}

    Turtlesim.sysml

    /*============================================================
    The turtlesim ROS package: its message type, and the stock node
    itself declared as a PLATFORM-PROVIDED COMPONENT.

    Structural convention (see doc/ros/PlatformProvidedTypes-design.md):
    SysML package name = ROS package name; for a message, part def
    name = message name (turtlesim::Pose -> turtlesim/msg/Pose); for a
    component, part def name = executable name
    (turtlesim::turtlesim_node -> `ros2 run turtlesim turtlesim_node`).
    Both live in this one package because the ROS package turtlesim
    contains both.

    The structure/ variant's copy of this file declares only Pose and
    leaves the node off-model.  Declaring the node -- the sole
    difference between the two copies -- is what brings the cVel and
    cPose connections back, and with them datatype checking and the
    generation-time topic-name checks.

    Codegen emits NO code for a platform-provided component -- only
    deployment artifacts: a launch entry (the subcomponent usage name
    becomes the node name) and an exec_depend on the turtlesim package
    so `rosdep install` pulls the stock node.
  ============================================================*/

package turtlesim {
    private import HAMR_AADL_Preview::*;
    private import HAMR::*;

    // turtlesim/msg/Pose
    //   native: float32 x, y, theta, linear_velocity, angular_velocity
    part def Pose :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;

        part x                : Base_Types::Float_32;
        part y                : Base_Types::Float_32;
        part theta            : Base_Types::Float_32;
        part linear_velocity  : Base_Types::Float_32;
        part angular_velocity : Base_Types::Float_32;
    }

    part def turtlesim_node :> Thread {
        attribute :>> Component_Provenance = Provenances::Platform_Provided;

        // Optional: the structural convention above already yields
        // turtlesim/turtlesim_node.  Native_Name is the escape hatch for a node
        // whose package/executable names do not match the model's.
        // attribute :>> Native_Name = "turtlesim/turtlesim_node";

        // Periodic with data ports, and the two go together -- both follow from
        // how turtlesim actually runs: a ~16 ms frame update that consumes the
        // LATEST stored Twist, zeroing it after a 1 s command timeout, while the
        // subscription callback only stores.  That is last-value-wins sampling,
        // not queued event dispatch, so there is no arrival to dispatch on and
        // no queue to model.
        //
        // None of this reaches the ROS 2 backend -- no code is generated for a
        // platform-provided component -- so these attributes are for scheduling
        // analysis and for the reader.
        attribute :>> Dispatch_Protocol = Periodic;
        attribute :>> Period = 16 [ms];

        // The node's built-in topics, declared with their own RELATIVE names.
        // These stay here at the definition rather than at the usage site: they
        // are facts about the stock node, not deployment configuration.  With
        // this component left un-namespaced at its usage site, they resolve to
        // /turtle1/cmd_vel and /turtle1/pose.
        in port cmdVel : DataPort {
            in :>> type : geometry_msgs::Twist;

            attribute :>> Ros_Topic_Name = "turtle1/cmd_vel";
        }

        out port pose : DataPort {
            out :>> type : Pose;

            attribute :>> Ros_Topic_Name = "turtle1/pose";
        }
    }
}

    RosMessages.sysml

    /*============================================================
    Platform-provided ROS 2 message types

    Mirrors of preexisting ROS 2 message types used by the Turtle
    Control system.  Structural convention (see doc/ros/PlatformProvidedTypes-design.md):
    SysML package name = ROS package name, part def name = message
    name, so geometry_msgs::Twist denotes geometry_msgs/msg/Twist.

    Twist is declared OPAQUE -- the minimum declaration, no fields.
    That is enough for codegen: it emits no .msg file for the type,
    uses the native ROS type as the payload of every port and topic
    carrying it, and adds geometry_msgs to the generated package
    dependencies.  What an opaque declaration does NOT give you is a
    vocabulary: nothing in the model can speak about the value's
    fields, and codegen generates no example builder for it, so
    application code constructs a Twist with native rclcpp calls.

    turtlesim::Pose, in Turtlesim.sysml, is the contrasting case: the
    same provenance, but with mirror fields.

    NOTE: Type_Provenance is a HAMR extension defined in the
    sysml-aadl-libraries.
  ============================================================*/

package geometry_msgs {
    private import HAMR::*;

    // geometry_msgs/msg/Twist
    //   native: Vector3 linear ; Vector3 angular
    part def Twist :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;
    }
}

/*============================================================
    rcl_interfaces::Log -- the /rosout payload.

    Declared here for the same reason geometry_msgs::Twist is: a
    port carries it, so the type must exist in the model, and it is
    a native ROS type rather than one HAMR generates.  It is left
    OPAQUE (no mirror fields) because nothing in this system reads a
    log record's contents at the model level -- the logger receives
    records and prints them.

    Note that no node here constructs a Log.  The encoder's rosout
    port is realized by the rcl logging infrastructure, not by
    application code, so the absence of an example builder for an
    opaque type costs nothing on the producing side.
  ============================================================*/

package rcl_interfaces {

    // rcl_interfaces/msg/Log
    part def Log :> Data {
        attribute :>> Type_Provenance = Provenances::Platform_Provided;
