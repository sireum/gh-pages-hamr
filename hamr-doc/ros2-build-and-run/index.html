    Building and Running ROS 2 Systems

    Chapter 4 of 4 in HAMR ROS 2 Development.

    The previous three chapters produced a workspace. This one builds it and runs it.

    Everything here applies to all three variants — the shape of the generated workspace does not depend on which modeling features you used. What changes is the node list.

    The complete source for all three variants is on the ROS 2 Example Models page.

    A system with micro-ROS nodes has an inherent awkwardness worth naming up front: it is two builds, not one. The rclcpp packages build from the generated workspace; the micro-ROS packages build inside a separate firmware workspace that is shared across projects and set up once. Most of what follows is a consequence of that split.

    The Generated Workspace

    Makefile                             the intended entry points
readme.md                            prerequisites and manual equivalents
src/
  <pkg>_interfaces/                  generated .msg files
  <pkg>/                             rclcpp nodes -- base_code + user_code
  <pkg>_bringup/                     launch files
microros_apps/
  colcon.meta                        firmware build configuration
  <pkg>_microros/                    micro-ROS nodes -- base_code + user_code

    Three things about this layout are worth explaining.

    The interfaces package is separate because both halves depend on it. The message definitions are generated once and built twice — once here for the rclcpp nodes, once inside the firmware workspace for the micro-ROS nodes, which need type support generated by rosidl_typesupport_microxrcedds rather than the standard one.

    microros_apps/ sits outside src/ deliberately. A plain colcon build from this directory must not pick those packages up: they are built elsewhere, against a different middleware. Keeping them out of src/ is what makes make build-ros2 safe to run.

    Makefile and readme.md are not overwritten by a regeneration, so anything you add to them survives. The same is true of the marked blocks inside colcon.meta and the launch files.

    Prerequisites

    A ROS 2 installation, and — if the model has any micro-ROS nodes — a micro-ROS firmware workspace.

    That workspace holds the micro-ROS client stack (rclc, rmw_microxrcedds, micro_ros_setup) and the micro-XRCE-DDS agent. It takes a while to build, and it is built once and shared across every micro-ROS project you have. Set MICROROS_WS to a stable location outside any individual project and put it in your shell profile:

    export MICROROS_WS=/path/to/microros_ws

    The generated readme.md carries the full one-time setup as copy-pasteable commands. In outline: clone and build micro_ros_setup, run create_firmware_ws.sh host to fetch the client stack, build it with build_firmware.sh, then create_agent_ws.sh and build_agent.sh for the agent.

    Every make target that touches the micro-ROS half fails immediately with a readable message if MICROROS_WS is unset, rather than getting halfway and producing something confusing.

    Building

    make build

    That runs three steps: check-ros2, which verifies ROS_DISTRO is set and the distribution’s setup.bash exists; build-microros, which copies the interfaces package and the generated micro-ROS packages into $MICROROS_WS/src/ and builds them there; and build-ros2, an ordinary colcon build in this workspace.

    Why the micro-ROS build runs under env -i

    The build-microros target is more careful than it looks:

    cd $(MICROROS_WS) && env -i HOME="$$HOME" PATH="$$PATH" ROS_DISTRO="$${ROS_DISTRO}" \
  bash --noprofile --norc -c "..."

    colcon records whatever is on AMENT_PREFIX_PATH and COLCON_PREFIX_PATH at build time into the setup scripts it generates, as a prefix chain. MICROROS_WS is shared across projects — so building into it with another workspace sourced would chain that workspace into MICROROS_WS permanently, for every project that sources it afterwards. Clearing only one of the two variables is not enough; both seed the chain.

    This is the kind of failure that shows up weeks later in an unrelated project, which is why the target scrubs the environment rather than trusting yours to be clean.

    Firmware Configuration

    microros_apps/colcon.meta configures the micro-ROS middleware — rmw_microxrcedds, microxrcedds_client, and the typesupport packages. Those live in the firmware workspace and were built by the one-time setup, not by make build, which builds only application packages.

    To have any effect it must be installed into that workspace. Sitting in microros_apps/ it does nothing, which is why this is its own step and deliberately not part of make build:

    make microros-config

    Run it once after generating, and again whenever colcon.meta changes. It installs the file as $MICROROS_WS/src/colcon.meta — the path micro_ros_setup’s host build reads — and rebuilds the micro-ROS stack with --cmake-force-configure. That flag matters: without it a changed colcon.meta can leave existing CMake caches in place, so the target reports success while the new settings never take effect.

    It displaces micro-ROS’s stock profile

    create_firmware_ws.sh seeds src/colcon.meta with its own profile, so there is normally a file there already. Since MICROROS_WS is shared across projects, the target renames it to colcon.meta.bak rather than discarding it.

    The two differ in ways worth knowing if you go looking:

    stock profile generated
    RMW_UXRCE_MAX_* generous fixed sizes derived from your model’s port counts
    UCLIENT_PROFILE_MULTITHREAD ON OFF

    Multithreading is off because generated micro-ROS nodes do not need it. Each node runs one rclc executor on one thread and releases all port traffic through sendOutputs at dispatch completion, so nothing ever drives the XRCE session from two threads at once — and the locking that setting adds is not free.

    If you maintain your own firmware configuration, merge the two rather than letting one replace the other.

    What fails quietly if you skip it

    • RMW_UXRCE_MAX_PUBLISHERS / RMW_UXRCE_MAX_SUBSCRIPTIONS are derived from the model’s port counts and regenerated on every run. If the firmware’s static pools are smaller than the nodes need, entity creation fails without a diagnostic. Re-apply after adding ports.
    • RMW_UXRCE_TRANSPORT and the agent address must agree with how you actually start the agent. These live in a preserved block, so changing them does not update the generated launch file’s agent command.
    • RCL_COMMAND_LINE_ENABLED restores the rcl argument parsing that micro_ros_setup disables in its cross-compiled configs. Without it, the rcl arguments in each node’s node_options block — topic remap rules in particular — are parsed by nothing.
    • RCL_LOGGING_ENABLED and RCL_LOGGING_IMPLEMENTATION are what make chapter 3’s rosout port do anything.

    Entries outside the marked blocks are derived from the model and overwritten on each run; the marked blocks are preserved. To override a derived value, restate its -D flag inside a marked block — colcon passes cmake-args through in order, and CMake takes the last occurrence.

    On a host workspace the rcl entry is inert

    A firmware workspace created for the host does not check out rcl at all. On host, micro-ROS is rmw_microxrcedds and rclc layered over the ROS 2 distribution’s own rcl — so there is no micro-ROS rcl to configure, and that one entry matches no package. The rest of the file applies normally: microxrcedds_client, rmw_microxrcedds, and the typesupport packages are all built there.

    This is usually invisible, because the distribution’s rcl is built with both argument parsing and logging enabled — the very things those flags turn on. Remap rules and /rosout routing therefore work on host whether or not the step is ever run.

    They stop working the moment the same model is deployed to an embedded target, where the micro-ROS rcl fork is used and ships with both features off. That is where applying the configuration matters, and an embedded workspace does check rcl out.

    One setting to revisit when moving off host: RCL_LOGGING_IMPLEMENTATION is emitted as rcl_logging_spdlog, which suits a host build. Embedded targets generally want rcl_logging_noop.

    Running

    Two ways, for two purposes.

    make launch     # everything from one launch file, in the foreground
make run        # a terminal per node

    make launch is the normal path. It builds, then runs ros2 launch on the generated bringup package. Output from every node is interleaved in one terminal.

    make run opens a separate terminal per node, with the agent started first and each window titled by node. When you are debugging one node’s behaviour, having its output in its own window is worth the extra windows. make stop kills everything it started.

    Both are alternatives to each other — neither is more correct.

    Launch arguments

    make launch LAUNCH_ARGS="log_file:=run1.txt"
make run ROS_ARGS="--ros-args -p log_file_name:=uros-demo.txt"

    These are not the same thing. LAUNCH_ARGS are launch arguments, declared by the launch file and reaching a node through its parameters — ros2 launch --show-args <bringup_pkg> <file>.launch.py lists what a file accepts. ROS_ARGS are rcl arguments, appended directly to each ros2 run. Either way, a node parameter must be declared by the node before a value takes effect.

    Both launch files carry preserved blocks for declaring arguments, so what you add survives regeneration.

    Three launch files, one system

    Generation emits the system in three pieces, in both XML and Python:

    File Contents
    <System>.launch.xml the whole system on this host — includes the two below
    <System>_ros2.launch.xml the rclcpp nodes only
    <System>_microros.launch.xml the agent plus the micro-ROS nodes

    The split is what makes deployment beyond a single host possible. The micro-ROS half is valid for a host deployment only — on an embedded target those nodes are flashed rather than launched, and the agent may run somewhere else entirely. In that case you launch the ROS 2 half alone:

    make launch LAUNCH_FILE=TurtleControlSystem_Instance_ros2

    XML and Python are generated from the same model and launch the same system. Pick whichever you would rather hand-edit; make launch defaults to Python and make launch-xml selects the other.

    The agent has to start first

    Micro-ROS nodes reach the ROS 2 DDS bus through a micro-XRCE-DDS agent. Start it before them — the generated run target sleeps two seconds after starting the agent for exactly this reason, and the _microros launch file lists it first.

    The agent’s transport must match RMW_UXRCE_TRANSPORT and the RMW_UXRCE_DEFAULT_UDP_* settings in colcon.meta. Because those live in a preserved block, changing them does not update the agent command in the generated launch file. If the nodes come up and never connect, check that these two agree.

    If the model does not contain everything

    Chapter 1’s structure variant does not model turtlesim, so nothing generated launches it — the launch file starts only what the model contains. Start it yourself alongside:

    ros2 run turtlesim turtlesim_node &
make launch

    You can also add it to the generated launch file, so one make launch brings up everything. Put the entry inside the preserved block — the launch file itself is regenerated, and only marked content survives:

    <!-- LAUNCH ARGUMENTS - additions within these tags will be preserved when re-running Codegen -->
<node pkg="turtlesim" exec="turtlesim_node" name="turtle"/>
<!-- LAUNCH ARGUMENTS - additions within these tags will be preserved when re-running Codegen -->

    That gets you a single command, but it is still deployment configuration rather than a statement in the model — the same trade as the remap rules it sits alongside. Nothing checks that the node you started is the one the pilot expects to talk to.

    Once turtlesim is modeled, as it is from chapter 2 onward, none of this is needed: the launch file starts it and the bringup package declares the dependency.

    Cleaning Up

    make stop     # kill running nodes and the agent
make clean    # remove build artifacts here AND the copied packages in MICROROS_WS

    make clean reaching into MICROROS_WS is intentional: build-microros copied packages in there, and leaving stale copies of a renamed or deleted package behind is a reliable way to get a confusing build later.

    Current Limitations

    • The one-time firmware setup is manual. Generation emits the instructions into readme.md but does not run them.
    • make run assumes gnome-terminal. On another desktop environment, edit the target — the Makefile is preserved across regeneration.
    • The agent command in the launch file does not track colcon.meta. Both are in preserved blocks; keeping the transport settings in agreement is manual.
    • Deploying the micro-ROS half to hardware is outside what generation automates. It emits the _ros2 launch file so the host side can be brought up independently, but flashing, the board-specific firmware workspace, and the transport wiring are yours.
