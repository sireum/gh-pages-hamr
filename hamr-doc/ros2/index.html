    HAMR ROS 2 Development

    Code-level development for ROS 2, covering what HAMR generates from a SysMLv2 model, how generated nodes bind to topics that already exist, and how to build and run the result.

    HAMR targets ROS 2 through two backends, chosen per thread by the Ros_Node_Kind property: rclcpp nodes for C++ components running on a host, and micro-ROS nodes for C components running on a microcontroller and reaching the DDS bus through a micro-XRCE-DDS agent. A single model may contain both, and the running example does.

    Before You Start

    These chapters assume you have read Model-Level Development with SysMLv2 and are comfortable with AADL threads, ports, and dispatch protocols as described in HAMR Semantics Building Blocks and Computational Concepts.

    You do not need to have read Code-Level Development for Microkit. If you have, the workflow will feel familiar — entry points, preserved blocks, and the implement-and-test loop work the same way — and these chapters concentrate on what is different about ROS 2.

    The Chapters

    They are written to be read in order. Each one takes the same system — a wheel encoder feeding a pilot that drives turtlesim — and adds what the previous one left out, so a chapter’s starting point is the one before it finishing.

    1. ROS 2 Component Development

    What code generation produces and what you write afterwards: the package layout, the split between generated base code and your preserved user code, how AADL datatypes become ROS messages, and how each dispatch protocol is realized on both backends. Ends with a system that runs, with two edges held together by deployment remaps.

    2. ROS 2 Topic Naming and Platform Integration

    Where topic names come from when the model does not supply them, and how to make the model supply them: namespaces, explicit topic names, relative versus absolute resolution, and declaring a stock ROS node such as turtlesim as a platform-provided component. Both remaps disappear, and those edges come under the same generation-time checking as every other connection.

    3. Infrastructure-Provided Ports

    Ports that refer to a communication path the platform already provides rather than declaring one for generation to realize. rosout is the implemented case: what the reserved name constrains, why an rclcpp node gets /rosout for free while a micro-ROS node does not, and why a connection that generates nothing is still worth drawing.

    4. Building and Running ROS 2 Systems

    The generated workspace and the Makefile targets that drive it — the two-build split between this workspace and the shared micro-ROS firmware workspace, applying the generated firmware configuration, the launch files, and starting the agent.

    The Models

    ROS 2 Example Models reproduces all three model variants in full, so the source can be read alongside any chapter without leaving the browser. Each chapter links to its own variant.
