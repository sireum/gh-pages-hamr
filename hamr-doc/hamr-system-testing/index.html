    HAMR System Testing on seL4 -- Overview

    This chapter provides an overview of system testing in HAMR: tests that run a whole composed system – the real Rust application code of every thread, on seL4, under the production schedule – and that a developer drives step by step to inject inputs, observe results, and check them. While the tests run, HAMR also checks every thread dispatch against the executable form of the model’s GUMBO component contracts and system-level properties, so a test catches contract violations it did not explicitly look for.

    The current state of the tool is a “usable prototype”. It is enabled with an experimental code generation option, runs on the QEMU simulator through a command-line driver, and has a few limitations listed in §12.

    The worked example throughout this chapter is the Struct Split system used in the GUMBO System-Level Properties chapter. Its system tests are in the HAMR-SysMLv2-Rust-seL4-P-DP-SysPropStructSplit-add-SysTest-solution project in the HAMR tutorials repository; every test and every line of test output below is quoted from that project and its runs, except in §6.1, which covers event ports and so uses a model that has them.

    We assume you have read the Manual Unit Testing chapter (the component-level testing idiom that system tests mirror), the Manual GUMBOX Testing and Property-Based Testing chapters (executable contracts as test oracles, and PropTest), and the GUMBO System-Level Properties chapter (the Struct Split model, its composition block, and its properties). The Microkit Folder Structure page describes the generated project layout this chapter extends.

    1. What system testing is (and why)

    HAMR’s other assurance techniques each look at part of the picture:

    Technique What runs Where What it establishes
    Manual unit tests, GUMBOX tests, property-based tests one thread’s entry points, in isolation the host (cargo test) the component meets its contract for the tested inputs
    Verus verification of components nothing – a proof the host the component meets its contract for every input
    System property verification nothing – a proof over the component contracts the host the system property holds, assuming every component meets its contract
    System testing every thread’s real code, composed, under the real schedule seL4 (QEMU) the composed system behaves as expected for the tested scenarios, and every contract held at every dispatch

    System property verification deliberately never looks at application code: it proves properties from the contracts. Unit tests and component proofs look at code, but one component at a time, on the host. System testing is the place where the actual implementations run together, on the actual platform, in the actual schedule – so it catches what falls between those techniques: a component that is not yet verified, a contract that is weaker than the developer thought, a scenario that spans several hyperperiods, or an integration fault no single component’s contract describes.

    The idea is not new to HAMR. On the JVM platform, HAMR provides a static scheduler with a command API (art.scheduling.static) for stepping through the schedule slot by slot or hyperperiod by hyperperiod, inspecting and injecting system state, and observing the results; HAMR’s JVM system testing framework is built on it (see the HAMR system testing case studies). This chapter describes the counterpart for seL4 Microkit systems written in Rust, whose commands mirror the JVM ones.

    A system test is written in Rust, in the same shape as a component test:

    fn struct_flows_through_each_stage() {
  inject_generated(sxy(37, -12));     // as if GenStruct had sent (37, -12)

  let _ = api::sstep(1); // splitter
  sys_assert_eq!(inspect::get_splitter_splitter_xfield(), Some(37));
  sys_assert_eq!(inspect::get_splitter_splitter_yfield(), Some(-12));

  let _ = api::sstep(1); // incx
  sys_assert_eq!(inspect::get_incx_incx_outxfield(), Some(38));
  ...
}

    It steps the schedule (api::), injects and inspects ports and GUMBO state variables (inspect::), asserts on what it sees, and, when it needs to, controls contract checking (observe::). The sections below take these in turn.

    2. Why system testing needs the MCS user-land scheduler

    HAMR generates seL4 Microkit systems under one of two scheduling models, selected by codegen’s --scheduling option (the Installation chapter describes the tools each needs):

    • Domain scheduling (the default). The seL4 kernel itself runs a fixed cyclic schedule of domains, described in microkit.schedule.xml; each thread is placed in its own domain, and a small pacer protection domain dispatches it when its domain’s slot begins. The kernel switches domains on its own timer.
    • MCS user-land scheduling (--scheduling UserLand). The threads’ protection domains are passive, and an ordinary user-level scheduler protection domain dispatches each one in turn by notifying it, timed by the sDDF timer driver. The system description is produced by a Python program (meta.py) rather than written as XML.

    Both run the same static schedule. The difference that matters here is who is in control of it. Under domain scheduling the schedule is enforced by the kernel: nothing a test could write can pause it after one slot, hold it while a value is injected, or ask it to run “until thread X is next”. Under user-land scheduling the schedule is a user-level program, so HAMR can generate a second scheduler – the test scheduler – that waits for commands instead of a timer. System testing is therefore available only for MCS user-land builds.

    The other chapters in this documentation use domain-scheduled examples, and nothing they show would change under MCS. Generating Struct Split both ways with the same version of HAMR produces byte-for-byte identical Rust crates – application code, unit tests, GUMBOX harnesses, Verus contracts, and the sys_nominal_proof system-property crate. What differs is only the infrastructure underneath them:

    Domain scheduling (hamr/microkit) MCS user-land scheduling (hamr/microkit_mcs)
    Rust crates (crates/) identical identical
    Who runs the schedule the seL4 kernel (domains) plus a pacer PD a scheduler PD plus the sDDF timer_driver PD
    System description microkit.system, microkit.schedule.xml meta.py (sdfgen)
    Generated C thread bridges and _MON wrappers the same files, wired to the scheduler instead of the pacer, plus a _MON_user.c hook per thread
    Extra build dependencies none LionsOS (for sDDF) and the sdfgen Python package
    System testing not available available (this chapter)

    Unit tests, GUMBOX tests, and Verus run on the host and never involve the scheduler at all, which is why the earlier chapters could use either model. To keep the existing tutorials unchanged, the Struct Split projects carry both builds side by side: hamr/microkit (domain scheduling, used by the system properties chapter) and hamr/microkit_mcs (user-land scheduling, used here). Each tree has its own copy of the application code; the copies are identical.

    3. How it works

    When system testing is enabled, codegen adds a test variant of the MCS build alongside the normal image. The test variant replaces the scheduler with the test scheduler and adds one more protection domain, the test controller, which runs your tests:

    ┌──────────────────┐     command      ┌──────────────────┐  dispatch  ┌──────────────┐
│ Test controller  │─────────────────▶│  Test scheduler  │───────────▶│ gen_gen      │
│ (runs tests.rs)  │◀─────────────────│                  │◀───────────│ splitter ... │
└──────────────────┘  status, parked  └──────────────────┘  completed │ consume      │
         │                                                            └──────────────┘
         │   reads and writes the threads' port and state-variable memory    ▲
         └───────────────────────────────────────────────────────────────────┘
    • The controller sends a command – “step one slot”, “run until splitter_splitter is next”, “finish this hyperperiod” – and the test scheduler dispatches threads, in the production schedule order, until the command is complete. Each thread tells the scheduler when its dispatch has finished, so stepping runs as fast as the threads do rather than waiting out each slot’s time budget. A watchdog still bounds each slot: a thread that does not finish in time fails the test that was running.
    • Between commands the schedule is paused: no thread runs, and the controller can read and write the memory regions the threads communicate through – their ports and their GUMBO state variables – without racing them.
    • The controller is the lowest-priority protection domain and owns no slot of the schedule, so the schedule under test is the production schedule, slot for slot.

    The production image is not changed. The normal image (plain make) contains no controller and no test scheduler; the test variant is a separate image built with make CONFIG=test_scheduler.mk, and the test driver (§9) builds it for you. A tests.rs that does not compile cannot break the production build.

    4. Turning it on, and what codegen generates

    System testing is requested with an experimental codegen option on an MCS build:

    --platform Microkit --scheduling UserLand --experimental-options ENABLE_TEST_SCHEDULER

    In the Struct Split projects, run it through the project’s run-hamr.cmd from the model directory, pointing --sel4-output-dir at the MCS tree (the script adds the project’s other options – source path, output directory, package name):

    cd sysmlv2/struct-split
../bin/run-hamr.cmd --platform Microkit --scheduling UserLand \
    --experimental-options ENABLE_TEST_SCHEDULER --sel4-output-dir ../../hamr/microkit_mcs

    (--runtime-monitoring is not needed for system testing, but it does no harm: it adds HAMR’s runtime-monitor variants beside the test variant.)

    Note

    The CodeIVE’s “HAMR SysML CodeGen” command uses the first //@ HAMR: configuration in the model whose platform matches. The Struct Split model’s configuration line is the domain-scheduled one, so regenerate the MCS tree from the command line as shown above.

    Beyond the normal MCS build, codegen generates:

    hamr/microkit_mcs/
  test_scheduler.meta.py          # the test variant's system description
  test_scheduler.mk               # selected by: make CONFIG=test_scheduler.mk
  scheduler/src/test_scheduler.scheduler.c
  scheduler/include/test_scheduler.*.h
  bin/run-tests.cmd               # the host-side test driver (§9)
  crates/
    observers/                    # the executable contract checks (§8)
    test_controller/
      src/system_tests/
        api.rs                    # stepping commands
        inspect.rs                # get_/put_/set_ accessors for this model's ports and state variables
        observe.rs                # contract-check control: expect, take, switches
        harness.rs                # the runner, system_tests!, sys_assert!, run_property
        selection.rs, mod.rs
        tests.rs                  # YOUR TESTS -- written once, never overwritten

    Everything in the controller crate is regenerated on every codegen run except tests.rs, which codegen writes once, with two small smoke tests and a commented overview of the API, and then preserves – the same arrangement as a component crate’s src/test/tests.rs.

    The generated smoke tests check the test machinery itself, not the model:

    system_tests! {
  suite smoke {
    fn schedule_advances_by_hyperperiod() {
      let before = api::info_state();
      let after = api::hstep(1);
      sys_assert!(after.flags & api::FLAG_BAD_COMMAND == 0);
      sys_assert_eq!(after.hyperperiod_num, before.hyperperiod_num + 1);
    }

    fn stepping_one_slot_at_a_time_wraps() {
      let n = api::schedule().num_timeslices;
      let before = api::info_state();
      let mut i = 0;
      while i < n {
        let _ = api::sstep(1);
        i += 1;
      }
      let after = api::info_state();
      sys_assert_eq!(after.current_timeslice, before.current_timeslice);
      sys_assert_eq!(after.hyperperiod_num, before.hyperperiod_num + 1);
    }
  }
}

    The first asks the scheduler for one hyperperiod and checks that the command was accepted and the hyperperiod count advanced by exactly one; the second steps through the schedule one slot at a time and checks that it arrives back at the same slot one hyperperiod later. Because they use only api::, they compile for every model, so a freshly generated project has tests that run before you have written any. A passing run of them confirms the whole path: the test image builds, every thread initializes on seL4 (init=ok), the controller can drive the scheduler, and every dispatch completes within its slot’s watchdog. They also exercise the contract checks of §8, since every slot they step through is a checked dispatch – §10 shows them failing on a seeded bug even though they assert nothing about the model. Keep them, or replace them with tests of your own; codegen does not write them again.

    For Rust threads with GUMBO state variables, codegen also adds a few accessors to the thread’s bridge code so that a test can inject a state variable’s value; these are inert in the normal image.

    5. Writing a system test

    5.1 Declaring tests

    Tests are declared inside one system_tests! block in tests.rs, grouped into suites:

    system_tests! {
  suite pipeline {
    fn struct_flows_through_each_stage() { ... }
    fn x_saturates_at_the_upper_bound() { ... }
    fn lower_bound_passes_through() { ... }
  }
  suite properties {
    fn end_to_end_holds_for_random_structs() { ... }
  }
  suite robustness { ... }
}

    Each test is registered under its qualified name (pipeline::x_saturates_at_the_upper_bound), which is also what the test filter matches (§9). A larger collection can be split across files: replace the block in tests.rs with system_test_files! { mod nominal_tests; mod fault_tests; } and give each file under system_tests/tests/ its own system_tests! block. Keep the _tests.rs suffix, which the model’s clean script preserves.

    Why a macro rather than #[test]? The controller is a no_std program running on seL4, where cargo test’s test collection does not exist; the macro builds the table of tests that the generated runner walks.

    5.2 Stepping the schedule: api::

    Command Effect JVM equivalent
    api::sstep(n) step through the next n schedule slots, padding slots included; any n (it wraps into later hyperperiods), and sstep(0) does nothing Sstep(n)
    api::hstep(n) finish the hyperperiod in progress, then n - 1 more Hstep(n)
    api::run_to_thread(ch) run until the given thread’s slot is next (it has not run yet); returns at once if it already is RunToThread(name)
    api::run_to_slot(n) run until slot n is next, wrapping into the next hyperperiod if needed; returns at once if it already is. n is a slot index, 0 to num_timeslices - 1 RunToSlot(n)
    api::run_to_hp(n) run until hyperperiod n begins; n must be later than the current hyperperiod RunToHP(n)
    api::run_to_state(hp, slot) run until (hyperperiod, slot), which must not be in the past RunToState(hp, slot)
    api::info_state() current position, without dispatching anything Infostate
    api::schedule() the schedule: slot count, each slot’s channel and length Infoschedule

    Threads are named for run_to_thread by generated constants, one per thread: inspect::channels::splitter_splitter_MON. A target outside these limits – a slot index past the end of the schedule, a hyperperiod already passed, a channel that is not in the schedule – is rejected by the scheduler, which fails the test. Every command returns the scheduler’s status (hyperperiod_num, current_timeslice, …), and a command that fails – a thread overran its slot, or the target was unreachable – fails the running test automatically; that is why the examples can discard the result with let _ =.

    Struct Split’s MCS schedule is one slot per thread, in the order the system properties chapter’s schema allows, followed by a padding slot:

    slot:   0     1         2     3     4       5       6        7
        gen   splitter  incx  decy  clampx  merger  consume  (pad)

    5.3 Observing and injecting: inspect::

    For every port and GUMBO state variable, inspect.rs provides a getter and a setter named after the thread that owns the memory:

    inspect::get_incx_incx_outxfield()            // -> Option<i32>
inspect::get_consume_consume_sv_last_x()      // GUMBO state variable last_x
inspect::put_gen_gen_outstruct(s)             // write GenStruct's output port

    Getters return Option – None when the port or state variable holds no value yet. A data port with a producer is stored in its producer’s output region, so writing it means acting as the producer: put_gen_gen_outstruct makes every consumer of GenStruct’s output receive the injected struct.

    For setting up a thread’s inputs, use the generated pre-state containers instead: one struct per thread holding every input port and every GUMBO state variable of that thread, and a set_<thread> function that writes them all:

    pub struct merger_merger_PreState {
  pub inxfield: i32,       // produced by clampx
  pub inyfield: i32,       // produced by decy
}
pub fn set_merger_merger(s: merger_merger_PreState) { ... }

pub struct consume_consume_PreState {
  pub instruct: StructXY,  // produced by merger
  pub sv_last_x: i32,      // GUMBO state variable
}

    Fields are named as the consuming thread sees them. Data inputs and state variables are plain values; an event or event data input is an Option, where None means nothing is pending (§6.1). The containers deliberately have no Default: a Rust struct literal must name every field, so the compiler – not the developer’s vigilance – guarantees that a test’s setup is complete, and adding a state variable to the model later breaks every test that has not accounted for it (see §6).

    When to inject. A producer that runs after your injection overwrites it. So inject after the producer has run and before the consumer runs: park with run_to_thread(<consumer>), set, then step. Struct Split’s tests use one helper for the most common case:

    /// Injects `g` as the struct GenStruct sent this hyperperiod.
fn inject_generated(g: StructXY) {
  let _ = api::run_to_thread(channels::splitter_splitter_MON);
  inspect::set_splitter_splitter(inspect::splitter_splitter_PreState { instruct: g });
}

    Every test starts at slot 0 of a hyperperiod (§6), so run_to_thread(splitter) stops right after GenStruct has run and before SplitStruct reads its output. The injected struct replaces the one GenStruct sent – for every downstream thread, and also for the system-level assertions of §8, which treat it as that hyperperiod’s gen_out.

    5.4 Asserting: sys_assert!

    Tests assert with sys_assert!(cond) and sys_assert_eq!(a, b), not assert!. A failing sys_assert* records the failure (with file, line, and condition), and returns from the test, and the runner continues with the next test. A panic would instead take the controller’s protection domain down and end the whole run.

    Putting the pieces together, the first Struct Split test follows one struct through every stage, checking each thread’s output right after it runs:

    fn struct_flows_through_each_stage() {
  inject_generated(sxy(37, -12));

  let _ = api::sstep(1); // splitter
  sys_assert_eq!(inspect::get_splitter_splitter_xfield(), Some(37));
  sys_assert_eq!(inspect::get_splitter_splitter_yfield(), Some(-12));

  let _ = api::sstep(1); // incx
  sys_assert_eq!(inspect::get_incx_incx_outxfield(), Some(38));

  let _ = api::sstep(1); // decy
  sys_assert_eq!(inspect::get_decy_decy_outyfield(), Some(-13));

  let _ = api::sstep(1); // clampx: 38 is in range, so it passes through
  sys_assert_eq!(inspect::get_clampx_clampx_outxfield(), Some(38));

  let _ = api::sstep(1); // merger
  sys_assert_eq!(inspect::get_merger_merger_outstruct(), Some(sxy(38, -13)));

  let _ = api::sstep(1); // consume latches the x field it received
  sys_assert_eq!(inspect::get_consume_consume_sv_last_x(), Some(38));
}

    A test need not step slot by slot. The boundary tests run to the end of ConsumeStruct’s dispatch and check only the results:

    /// Runs to the end of ConsumeStruct's dispatch.
fn run_through_consume() {
  let _ = api::run_to_thread(channels::consume_consume_MON);
  let _ = api::sstep(1);
}

// At the top of GenStruct's range IncX produces 101, which ClampX saturates back
// to 100: the only case where the x field arrives unchanged.
fn x_saturates_at_the_upper_bound() {
  inject_generated(sxy(100, 100));
  run_through_consume();
  sys_assert_eq!(inspect::get_incx_incx_outxfield(), Some(101));
  sys_assert_eq!(inspect::get_merger_merger_outstruct(), Some(sxy(100, 99)));
  sys_assert_eq!(inspect::get_consume_consume_sv_last_x(), Some(100));
}

    6. Test isolation: set every input

    Each thread’s initialize entry point runs once, when the system boots; there is no way to return the system to its boot state between tests. So instead of resetting, system tests follow a discipline:

    • Tests must be order-independent and establish their own preconditions. Whatever the previous test left in a port or state variable is what this test starts with.
    • Set every input you depend on, not just the one you vary – otherwise the test silently inherits the previous test’s value. The pre-state containers (§5.3) make this checkable by the compiler.
    • The runner normalizes the schedule position: before each test it advances to slot 0 of a fresh hyperperiod, so hstep(1) or run_to_thread(..) means the same thing in every test.

    These rules are also what make it sound to run any subset of the tests (§9).

    6.1 Event inputs: what is pending

    Struct Split has only data ports, which always hold one value; “set every input” just means writing each one. An event or event data input is different: what matters is whether an event is pending for the thread when it is next dispatched, and an event the thread has not yet taken survives the runner’s normalization between tests – for example one sent, or injected, after the consumer’s slot in a frame. Without a way to say “nothing pending”, a test would inherit it.

    So in the pre-state containers every event and event data input is an Option:

    • Some(v) – exactly v is pending for the thread at its next dispatch;
    • None – nothing is pending.

    Data inputs and GUMBO state variables stay plain values, and the containers still have no Default, so every event input must be named with one or the other. For a single port, inspect::clear_<thread>_<port>() discards everything pending for that thread on that port. A clear takes effect at the start of the thread’s next dispatch, before it reads any port, and it is per consumer: other threads receiving from the same output keep what is pending for them.

    The examples in this subsection are from the SystemTesting model in HAMR’s code generator tests (hamr/codegen/jvm/src/test/resources/models/SystemTesting in the Sireum repository), since Struct Split has no event ports. In it, src sends on an event data port val that fans out to two consumers, dst1 and dst2, which run after it in that order; dst1 also has an unconnected event data input cmd. The tests use two small helpers: one that parks before dst1 after src has run, and one that builds dst1’s container:

    /// dst1's whole pre-state: `val` as given, nothing pending on ping or cmd, `latest` set.
fn dst1(val: Option<i32>, latest: i32) -> inspect::d1p_dst_PreState {
  inspect::d1p_dst_PreState { val, ping: None, cmd: None, sv_latest: latest, sv_gotCmd: false }
}

    Clearing one consumer leaves the other alone – dst2 is told nothing is pending, so only dst1 receives what src sent:

    fn clearing_one_consumer_leaves_the_other() {
  before_dst1(5);                     // src has sent 5 on val
  inspect::set_d2p_dst(inspect::d2p_dst_PreState { val: None });
  let _ = api::hstep(1);
  sys_assert_eq!(inspect::get_d1p_dst_ack(), Some(5));
  sys_assert_eq!(inspect::get_d2p_dst_fwd(), None);
}

    The consumers of one output receive the same events, so a Some sets the output for every consumer given Some, and the only per-consumer choice is Some versus None. Giving two consumers of one output different Some values fails the test with setup conflict on <connection>: ...; the consumers of one connection receive the same events.

    Setters work in batches: the setter calls between two scheduler commands. Within a batch their order does not matter – None for dst1 and Some(7) for dst2 give the same result whichever is written first. A batch ends at any api:: command (even one that dispatches nothing, such as info_state()), at the start of each test, and at an explicit put_ on that output, which is a deliberate send that every consumer receives. So set up all the consumers of an output between the same two commands.

    The contract checks follow a clear: a cleared event is not counted in that thread’s GUMBO checks, and for an unconnected input it disappears from the system assertions as well. A producer’s output still shows what it sent, since a system assertion about a producer’s output describes what the frame carried – clearing every consumer of val leaves the composition’s assertions about what src sent unchanged.

    7. Property-based system tests

    System tests can draw their inputs at random, like the component-level property-based tests. The controller crate includes PropTest, built to run on seL4, and the runner provides run_property(cases, make_strategy, property): it builds the strategy, runs cases random cases, shrinks a failing case to a minimal input, and returns whether every case passed. Each case drives the real system – inject, step, observe – exactly as a fixed-value test does.

    Struct Split’s property test is the run-time counterpart of the End_To_End_Functional system property, which system property verification proves from the component contracts:

    /// What the pipeline should deliver for a generated struct `g`: x incremented and
/// saturated at 100 by ClampX, y decremented.
fn expected_merge(g: StructXY) -> StructXY {
  sxy(if g.x < 100 { g.x + 1 } else { 100 }, g.y - 1)
}

fn end_to_end_holds_for_random_structs() {
  sys_assert!(run_property(32, || (-100i32..=100, -100i32..=100), |(x, y)| {
    let g = sxy(x, y);
    inject_generated(g);
    run_through_consume();
    proptest::prop_assert_eq!(inspect::get_merger_merger_outstruct(), Some(expected_merge(g)));
    proptest::prop_assert_eq!(inspect::get_consume_consume_sv_last_x(), Some(expected_merge(g).x));
    Ok(())
  }));
}

    The proof says the property holds if every component meets its contract; this test checks that the actual implementations deliver it.

    run_property takes a function that builds the strategy (|| ...), not the strategy itself. The controller has no operating system, so its heap is a fixed region that run_property sets up the first time it runs. Building a strategy can allocate (prop_flat_map, .boxed(), and prop_oneof! all do), and an argument expression would be evaluated before run_property had set up the heap. Passing a closure defers building the strategy until the heap exists.

    Seeds and reproducing a failure. There is no source of randomness on the target, so the cases are determined by a seed, PROPTEST_SEED, built into the test image. The test driver picks a fresh seed for every run, so each run explores new cases, and prints it:

    TEST | INFO  32 generated cases passed (PROPTEST_SEED=97a60469bc9618397801a46215b7e11b83e8bfdf44c6dbc3941ac106bb4497ff)

    A failure prints the shrunk input and the seed to pass back to reproduce the run (PROPTEST_SEED=<seed> bin/run-tests.cmd); §10 shows one. Cases share the running system, just as tests do, so each case must set what it depends on.

    8. Contract checking during tests

    Assertions in a test check what the test author thought to check. In addition, while the tests run, the controller checks every dispatch of every thread against the executable forms of the model’s specifications:

    • the GUMBO layer – each thread’s component contracts: its initialize guarantees (once, at boot), and at every dispatch its compute assumptions and integration assumptions (CEP_Pre) and its compute guarantees and integration guarantees (CEP_Post). These are the same GUMBOX predicates the component test harnesses use;
    • the system layer – for each composition in the model, every place assertion of every concrete property, checked as the schedule passes that place.

    Both layers are generated whenever the model has the corresponding specifications, and both are on by default. A violation fails the test that caused it, even if the test asserted nothing about it. This is why even the two generated smoke tests, which only check the scheduler, end up checking Struct Split: every slot they step through is a checked dispatch. §10 shows the layers catching a seeded bug.

    A violation is reported as a VIOLATION line naming the contract and where the schedule was:

    TEST | VIOLATION CEP_Post incx_incx hp=2 slot=2
TEST | INFO  incx_incx pre: PreState_incx_incx { api_inxfield: 37 }
TEST | INFO  incx_incx post: PostState_incx_incx { api_outxfield: 39 }
TEST | VIOLATION SysAssert nominal/End_To_End_Functional at after incx hp=2 slot=2

    A test controls this checking through a third generated module, observe:: (observe.rs, generated when the model has contracts), alongside api:: and inspect::. It hosts the two layers – reading the threads’ ports and state variables at every dispatch, running the checks, and recording each violation against the running test – and gives the test a say in what becomes of a violation:

    Item Purpose
    observe::expect(e) declare a violation this test causes on purpose: a matching one prints as INFO expected violation instead of failing the test, and the test fails if it never happens (§8.2)
    Expect::CepPre(thread), Expect::CepPost(thread), Expect::SysAssert(composition, property) what to expect; a SysAssert expectation names a property, not one of its assertion points
    observe::take() hand the test the violations recorded so far that no expectation matched; taken violations no longer fail the test. The result has count(), iter(), and contains(e), and each violation its kind, thread, property, point (e.g. "before consume"), hp, and slot
    observe::Thread::splitter_splitter, observe::sys::nominal::End_To_End_Functional generated names for threads, compositions, and their properties, so a misspelling is a compile error
    observe::set_gumbo(on), observe::set_sysverif(on) turn a layer’s checking off or on for the rest of the test (§8.3)

    8.1 A broken assumption rejects the dispatch

    A thread’s CEP_Pre is its contract with whoever sends it data. When it does not hold, the controller reports CEP_Pre, fails the test, and rejects the dispatch: the thread’s slot passes without running it, so the out-of-contract values never reach its code. (HAMR’s runtime monitors, by contrast, only report a failed assumption.) Because the rejected thread produced nothing in that frame, the system layer suspends its assertions until the next hyperperiod, and says so.

    8.2 Tests that cause a violation on purpose

    A robustness test drives the system outside its contracts deliberately and must say which violation it expects. observe::expect(..) declares it: a matching violation is reported as INFO instead of failing the test, and the test fails if the violation does not occur. SplitStruct assumes its input struct lies in [-100, 100]:

    // SplitStruct assumes its input lies in [-100, 100] (an integration assume).
// A struct outside it fails SplitStruct's CEP_Pre, so the controller rejects
// the dispatch: SplitStruct does not run, and the out-of-range x never enters
// the pipeline.  The test declares the violation it causes.
fn out_of_range_struct_is_rejected_by_splitter() {
  observe::expect(observe::Expect::CepPre(observe::Thread::splitter_splitter));
  inject_generated(sxy(150, 0));
  let _ = api::sstep(1); // splitter's slot passes without dispatching it
  sys_assert!(inspect::get_splitter_splitter_xfield() != Some(150));
}

    TEST | BEGIN robustness::out_of_range_struct_is_rejected_by_splitter
TEST | INFO  expected violation: CEP_Pre splitter_splitter hp=37 slot=1
TEST | INFO  channel 3 not dispatched at hp=37 slot=1: its inputs did not meet its CEP_Pre; system assertions suspended until the next frame
TEST | PASS  robustness::out_of_range_struct_is_rejected_by_splitter

    Expect can name a thread’s CepPre or CepPost, or a system property: Expect::SysAssert(observe::sys::nominal::COMPOSITION, observe::sys::nominal::End_To_End_Functional). A SysAssert expectation matches any violation of that property, at any of its assertion points – which can hide a second, unrelated fault that breaks the same property. When the point matters, take the violations instead with observe::take() and assert on them; violations taken this way no longer fail the test (they are still printed).

    The second robustness test uses that to show a fault that only the system layer can see: it corrupts the y value on its way into MergeStruct, as a faulty channel might. Every thread still meets its own contract – MergeStruct copies what it receives, and the value lies within every range – but the end-to-end property no longer holds:

    fn corrupted_merge_input_breaks_end_to_end() {
  inject_generated(sxy(10, 20));
  let _ = api::run_to_thread(channels::merger_merger_MON);
  inspect::set_merger_merger(inspect::merger_merger_PreState { inxfield: 11, inyfield: 20 });
  run_through_consume();
  sys_assert_eq!(inspect::get_merger_merger_outstruct(), Some(sxy(11, 20)));

  let violations = observe::take();
  sys_assert_eq!(violations.count(), 1);
  sys_assert!(violations.iter().all(|v|
    v.kind == observe::Kind::SysAssert &&
    v.property == observe::sys::nominal::End_To_End_Functional &&
    v.point == "before consume"));
}

    TEST | BEGIN robustness::corrupted_merge_input_breaks_end_to_end
TEST | INFO  system assertions resumed at hp=38
TEST | VIOLATION SysAssert nominal/End_To_End_Functional at before consume hp=38 slot=5
TEST | PASS  robustness::corrupted_merge_input_breaks_end_to_end

    (The first INFO line is the previous test’s rejected dispatch ending: the system layer resumes at the new hyperperiod.)

    8.3 Turning checks off

    Each layer can be turned off at three levels:

    Level How Scope
    Build GUMBO_CHECKS=off / SYSVERIF_CHECKS=off in run-tests.cmd’s environment the whole run; the layer is not tracked at all
    Suite suite fault_injection(gumbo = off) { ... } every test in the suite
    Test observe::set_gumbo(false) / observe::set_sysverif(false) the rest of that test

    The runner restores the build-level setting after every test, so a test cannot leave checks off for the next one. A suite or test cannot turn on a layer that the build turned off. Turning checks off is the blunt tool; for a test that trips one contract on purpose, prefer observe::expect or observe::take, which keep every other contract checked.

    9. Running the tests

    Requires the seL4 Microkit SDK, LionsOS, sdfgen, and qemu-system-aarch64 (see Installation). The driver uses sh and pkill to stop QEMU, so it does not run on Windows. Like HAMR’s other .cmd scripts it runs itself through Sireum, so SIREUM_HOME must be set. From the MCS tree:

    cd hamr/microkit_mcs
bin/run-tests.cmd                 # every test
bin/run-tests.cmd pipeline::      # one suite
bin/run-tests.cmd saturates       # every test whose name contains "saturates"
bin/run-tests.cmd --list          # list the tests; run nothing

    The filter is a substring of the qualified suite::test name. run-tests.cmd builds the test image (a debug build, which it forces, since the test output is printed with debug printing), boots it under QEMU, reads the serial output, stops QEMU when the run is done, and exits with a nonzero code unless every selected test passed. The first build takes a minute or two; changing only the filter, the seed, or the check switches afterwards relinks the image in seconds. The environment variables PROPTEST_SEED, GUMBO_CHECKS, and SYSVERIF_CHECKS are passed through to the build.

    The output that matters is every line beginning TEST | . The serial console is the only channel that carries results off the target, and it also carries everything else the system prints – the loader and kernel boot messages, the scheduler’s SCHEDULER | ... lines, each thread’s own logging – so the controller marks its lines with a prefix, and the driver reads only lines that start with TEST | . (Anchoring at the start of the line means a message that merely mentions DONE cannot end the run early.)

    TEST | LIST  smoke::schedule_advances_by_hyperperiod
...
TEST | LIST  robustness::corrupted_merge_input_breaks_end_to_end
TEST | BEGIN smoke::schedule_advances_by_hyperperiod
TEST | PASS  smoke::schedule_advances_by_hyperperiod
...
TEST | BEGIN pipeline::x_saturates_at_the_upper_bound
TEST | PASS  pipeline::x_saturates_at_the_upper_bound
...
TEST | DONE  matched=8 passed=8 failed=0 init=ok
OK: 8 of 8 tests passed
    • LIST lines are the table of registered tests (with (not selected) after those the filter leaves out); BEGIN, then PASS or FAIL, bracket each test; INFO and VIOLATION lines appear in between.
    • A failing test prints one FAIL line naming its first failure – a sys_assert* (<file>:<line> <condition>), a failed command, or contract violation (<n> in this test) – and any further failures as INFO also failed: ....
    • DONE closes the run: matched tests selected, how many passed and failed, and init=ok when every thread’s initialize guarantee held at boot.

    The driver’s verdict is deliberately strict, because the typical failure of a bare-metal run is silence – a hang, a crash, a controller that never started. A run fails unless it ends with a DONE line, the filter matched at least one test (a mistyped filter fails loudly rather than passing with nothing run), the PASS/FAIL lines reconcile with the counts, and init=ok.

    Reading the output:

    • The smoke tests fail even though they assert nothing about Struct Split: IncX’s compute guarantee (outxfield == inxfield + 1) failed at a dispatch they stepped through, and the INFO lines show the values it was checked on.
    • The system layer locates the fault in the schedule: End_To_End_Functional first breaks after incx, and stays broken at every later place of the frame. At the top of the range the bug also pushes x outside the ranges the other two properties carry (Merged_In_Consume_Range, Consume_Range_Loop_Invariant).
    • The test’s own assertion reports what it expected (== Some(101)), and its contract violations follow as also failed.
    • The property test shrinks to the simplest failing input, (0, 0), and prints the seed that reproduces the run.
    • The one test that still passes is the CEP_Pre robustness test: SplitStruct rejects the out-of-range struct, so nothing reaches IncX in that frame.

    The same bug would be found by IncX’s own unit tests and by Verus. The point of the exercise is that system tests do not depend on those having been written or run: the contracts travel with the model and are checked at every dispatch of the composed system.

    11. Authoring workflow and tips

    1. Generate, then list. After enabling the option, run run-tests.cmd --list first: it confirms the toolchain, the build, and the boot without running anything, and shows the generated smoke tests.
    2. Start from the dataflow. Decide which thread’s input you control and which outputs you observe; inject after the producer and before the consumer (run_to_thread(<consumer>)), and use the set_<thread> containers so the compiler checks that your setup is complete.
    3. Write helpers for the common moves – inject_generated, run_through_consume – so each test reads as its scenario.
    4. Check intermediate values while developing a test (sstep(1) and a get_), then simplify to the outputs that matter.
    5. Let the contracts do the routine checking. A test’s own assertions should state the scenario’s expected result; “every thread stayed within its contract” is checked for you.
    6. Name the violations you cause. Use observe::expect for a robustness test; use observe::take() when the property is checked at several places and the place matters.
    7. Mind what an injection means to the system layer. An injection into a producer’s output becomes that frame’s value of the port, so the system assertions judge the injected value – as inject_generated relies on. An injection further downstream (as in corrupted_merge_input_breaks_end_to_end) can contradict what was sent upstream, which the system layer reports.
    8. Keep tests short in hyperperiods. Each test runs on the real system; property tests multiply that by the number of cases. Reproduce failures with the printed PROPTEST_SEED rather than by raising the case count.

    12. Current limitations

    • MCS user-land scheduling only (§2), on the QEMU simulator, through a driver that does not run on Windows.
    • No reset between tests. Initialization runs once at boot; tests must be order-independent and set every input (§6).
    • Single-element event queues. With system testing enabled, codegen rejects a thread with GUMBO contracts that has a deeper event queue.
    • Debug builds only. Test output uses the debug console; the driver forces a debug build.
    • No interactive mode. Tests are compiled into the image; there is not yet a console for stepping the schedule by hand.
